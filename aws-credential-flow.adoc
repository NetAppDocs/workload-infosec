= AWS credential flow in NetApp Workload Factory
:hardbreaks:
:nofooter:
:icons: font
:linkattrs:
:imagesdir: ../media/

[.lead]
This flow shows how role identifiers, external IDs, and short-lived STS credentials are handled during onboarding and runtime operations.

== Credential data flow and retention path

image::aws-data-flow.png[AWS credentials data flow diagram]

[role="tabbed-block"]
====
.One-time setup
--
. Customer launches a CloudFormation stack (or manually creates an IAM role) in their AWS account.
. The IAM role trust policy specifies two conditions:
.. Only Workload Factory's service principal can assume it.
.. The caller must present the correct external ID.
. Workload Factory stores the role ARN and external ID (encrypted) in its database.
--

.Runtime (every API operation)
--
. Workload Factory retrieves the stored role ARN and external ID from MySQL.
. It checks Redis for a cached set of temporary credentials for this role.
. On cache miss, Workload Factory calls `sts:AssumeRole` with the role ARN, external ID, and a per-request session policy that restricts permissions to only the specific AWS actions needed for that operation.
. AWS STS returns temporary credentials (access key ID, secret access key, session token) with an expiration timestamp.
. Workload Factory caches these credentials in Redis and uses them to call the target AWS APIs.
. On cache hit, Workload Factory skips the STS call and uses the cached credentials directly.
--
====

== Session policy (least privilege per request)

Each STS call includes an inline session policy scoped to the minimum AWS actions required.

The primary reference for policy model details is link:least-privilege-requirements.html[Learn about least privilege requirements for Workload Factory^].
