= Workload Factory connections
:hardbreaks:
:nofooter:
:icons: font
:linkattrs:
:imagesdir: ../media/

[.lead]
The following list describes why each connection is needed:

* *Workload Factory to AWS APIs* (discovery and management): +
Used for DescribeFileSystems, DescribeVolumes, CreateVolume, UpdateVolume, DeleteVolume, CreateFileSystem, CreateBackup, DescribeBackups, plus EC2/VPC APIs for subnet and security group discovery. The Collector service scans approximately every 5 hours, with on-demand calls for all CRUD operations. All calls use STS-assumed temporary credentials with an ExternalId.

* *Workload Factory to customer AWS account resources* (orchestration and automation): +
Includes CloudFormation stack deployment (IAM role provisioning, FSx creation using templates), STS AssumeRole (cross-account access), CloudWatch alarm creation (monitoring Lambda), S3 presigned URL generation for CloudFormation templates, and `lambda:InvokeFunction` to trigger the Link Lambda.

* *Link Lambda to ONTAP management endpoint* (ONTAP REST/SSH not available through AWS APIs): +
Specific operations include EMS event retrieval, QoS/latency statistics, volume efficiency settings, aggregate capacity, SVM management, igroup/LUN operations, anti-ransomware status checks, SnapMirror configuration, NFS client information, and cluster version queries. Protocols: HTTPS/443 (REST) and SSH/22 (CLI). Link Lambda runs inside the customer VPC for private subnet access without exposing ONTAP publicly.

* *Link Lambda to AWS Secrets Manager* (ONTAP credential retrieval): +
Used only when the customer stores ONTAP admin credentials in Secrets Manager (alternative: credentials encrypted in Workload Factory MySQL using KMS envelope encryption). The proxy-forwarder passes `x-aws-secret-arn` (Base64-encoded) in headers; Link Lambda calls `GetSecretValue` to retrieve the password at execution time. This keeps the password within your account boundary and is never transmitted from Workload Factory.

* *Workload Factory and customer components to Amazon Bedrock* (AI features): +
Used only when AI features are enabled. Used exclusively by the Event Analyzer service for EMS analysis and latency diagnostics. Bedrock is called using your own assumed credentials and their inference profile ARN, so data does not flow to NetApp's account. Sent to Bedrock: EMS event JSON, QoS statistics, volume configuration, aggregate data, node information. Only active when AI features are explicitly enabled and an inference profile is configured per organization (`ai_analyzer_config` table).

Connections are grouped by the purpose they serve.

== Group B — ONTAP data plane

The ONTAP data plane is always proxied through Link, never direct.

[cols="2,2,1,3,3,4",options="header"]
|===
|Connection |Protocol |Port |Direction |Auth |Justification

|ONTAP REST API
|HTTPS
|443
|Link (in customer VPC) → ONTAP management LIF
|Basic auth (username/password) or Secrets Manager ARN
|Cluster, volume, and SVM configuration; QoS; EMS events; ARP status

|ONTAP SSH CLI
|SSH
|22
|Link (in customer VPC) → ONTAP management LIF
|Password auth
|Diagnostic commands (QoS stats, df, event logs, efficiency)
|===

Important: Workload Factory services never connect directly to ONTAP.

The proxy-forwarder resolves which Link to use through three strategies (priority order):

. Explicit `x-link-id` header: Looks up the Link Lambda ARN from the database.
. Target ID (FSx file system ID): Finds the associated Link.
. Agent/Connector ID: Routes through the message broker to the Connector.

== Group C — Link Lambda (deployed in your VPC)

[cols="2,2,1,3,3,4",options="header"]
|===
|Connection |Protocol |Port |Direction |Auth |Justification

|Lambda Invoke
|HTTPS (AWS SDK)
|443
|WF → AWS Lambda API (customer account)
|IAM (`lambda:InvokeFunction` permission)
|Execute ONTAP REST/SSH commands from within customer VPC

|Lambda → ONTAP
|HTTPS + SSH
|443, 22
|Lambda (customer VPC) → ONTAP management LIF
|Basic auth / password
|Private subnet access to ONTAP without public exposure
|===

Payload sent to Lambda:

* HTTPS: `{url, method, data, queryParams, endpoint (ONTAP IP), headers (Authorization), requestType: 'https'}`
* SSH: `{ssh: {command, host, username, password}, requestType: 'ssh'}`

Link Lambda requires outbound 443 (ONTAP REST, AWS APIs) and outbound 22 (ONTAP SSH) in its security group.

== Group D — Connector/NetApp Console Agent (EC2 in your VPC, outbound-only)

[cols="2,2,1,3,3,4",options="header"]
|===
|Connection |Protocol |Port |Direction |Auth |Justification

|Agent polling
|HTTPS
|443
|Connector (customer VPC) → WF message broker
|Bearer token (`occm-access` scope)
|Long-poll for pending ONTAP commands (7-second timeout; reconnects)

|Agent response
|HTTPS
|443
|Connector (customer VPC) → WF message broker
|Bearer token
|Return ONTAP command results (optionally zlib-compressed)

|Connector → ONTAP
|HTTPS + SSH
|443, 22
|Connector (customer VPC) → ONTAP management LIF
|Basic auth / password
|Execute proxied ONTAP operations
|===

Key design: Workload Factory never initiates inbound connections to the Connector. The Connector initiates all connections outbound. Work is queued in Redis streams; the Connector polls using `GET /message-broker/v1/requests`, retrieves tasks, executes them locally, and responds using `POST /message-broker/v1/responses`.

== Summary: network requirements for your VPC

[cols="2,2,2",options="header"]
|===
|Component |Inbound |Outbound

|FSx for ONTAP
|Port 443 and 22 from Link Lambda or Connector security group
|N/A

|Link Lambda
|None
|Port 443 (ONTAP, AWS APIs) and port 22 (ONTAP SSH)

|Connector EC2
|None
|Port 443 (WF endpoints, ONTAP, AWS APIs) and port 22 (ONTAP SSH)

|VPC endpoints (optional)
|N/A
|STS, FSx, S3, Secrets Manager, Lambda, CloudFormation
|===

No inbound internet access is required for any component in the customer VPC. All connections are either outbound-initiated (Connector polling) or invoked through AWS service APIs (Lambda Invoke).
