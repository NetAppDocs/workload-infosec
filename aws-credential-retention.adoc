= Workload Factory AWS credential retention
:hardbreaks:
:nofooter:
:icons: font
:linkattrs:
:imagesdir: ../media/

[.lead]
Workload Factory keeps credentials secure by:

* No long-term AWS access keys are ever stored. Workload Factory stores only a pointer (role ARN) and a shared secret (external ID). Neither grants AWS access on its own.
* Temporary credentials have a hard maximum lifetime of 1 hour (AWS-enforced), and Workload Factory caches them for at most 30 minutes before forcing a fresh STS call.
* If a cached token has fewer than 15 minutes remaining, it is discarded and a new token is obtained, ensuring operations never fail mid-execution due to credential expiry.
* Credential deletion by the customer immediately revokes Workload Factory's ability to access that account (the next AssumeRole call will fail, and cached tokens expire within minutes).

== Security controls

Workload Factory includes the following security controls:

* External ID prevents confused deputy attacks.
* Session policies enforce per-request least privilege.
* Temporary credentials are short-lived and refreshed before risky expiry windows.
* Regional and account-type handling differs for Standard, GovCloud, and China environments.
* Workload Factory never stores long-term AWS access keys.
* Workload Factory never modifies your IAM role's permissions.
* Workload Factory never escalates beyond the permissions granted by your role policy.
* Session policies can only reduce permissions; Workload Factory never expands them.

== ONTAP credential handling in Workload Factory

ONTAP credentials authenticate to the FSx for ONTAP file system management endpoint for operations not available through the AWS API (volume-level settings, performance diagnostics, and SVM configuration).

|AWS Secrets Manager
|You store credentials in your Secrets Manager; Workload Factory only holds the secret ARN reference.
|GovCloud (required), or when you prefer credentials never leave your account
|===

=== Credentials validation

Workload Factory periodically validates that stored credentials remain functional. Invalid credentials are flagged in the UI. Credentials that fail validation are rechecked after a 3-day backoff period.
